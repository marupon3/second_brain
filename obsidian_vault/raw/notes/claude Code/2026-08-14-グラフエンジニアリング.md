# 1つのウィンドウと1つのプロンプトから、1000以上のエージェントループを構築する（全5ステップ完全コース）

# Graph Engineering：Loop Engineeringの後継  
エージェントを10倍広く動かすワークフロー

## 概要
多くの人が作るマルチステップエージェントは「直線」になる。  
step1 → step2 → step3…と、前が終わるまで次が待たされる。

しかし、実際には半分のステップは待つ必要がない。  
ただキューに並び、コンテキストが溢れてエージェントが忘れるだけ。

遅かったのはモデルが弱いからではない。  
「作業はグラフなのに、線を描いてしまった」から。

このガイドでは、直線から「艦隊を広げて自分で検証するグラフ」へ移行する。  
5ステップで、実際に動くグラフを作り、現実で壊れる罠を指摘する。

---

## Chapter 0 - Graph Engineeringとは何か

1ヶ月前は「ループ」の話ばかりだった。  
Peter Steinbergerの9語：

> ループは「良くなる1サイクル」：  
> 試す → 結果を確認 → 調整 → 再び

これは「1つのエージェントが1つのことを繰り返し改善する原子」だ。

しかし単一ループには既知の失敗がある。  
例：サポートチームが「チケット解決率」だけにフィードバックループをかけた結果、  
数字は上がるが満足度は下がる（Goodhartの法則）。  
ループは自分のメトリクスしか見えない。

答えは「より良いループ」ではなく「ループのグラフ」＝  
互いに監視・修正し合うネットワーク。

エージェントではこうなる：
- 1つのエージェントに全部やらせるのをやめる
- 作業の「形」を設計する（何が先か、何が同時か、何が待つか）
- ノードが考える、エッジが結果を運ぶ

Claude Codeはこれを直接作るツールを出荷した：**Dynamic Workflows**

## Step 1 - 存在しないエッジを見つける

グラフの2要素：
- **ノード**：1単位の作業（1エージェント・1ジョブ・1入力・1出力）
- **エッジ**：依存関係（このノードの出力が次の入力になる）

誰もが犯すミス：「and then」をエッジだと思うこと。

例：「このファイルを要約して、そして天気を教えて」  
天気は要約を読まない。独立した2つの仕事なのに、線形スクリプトが無駄に繋いでいる。

習慣：
> すべての「and then」に対して聞く  
> 「次のステップは本当に前の出力を読んでいるか？」  
> - Yes → 本物のエッジ。順序を保つ  
> - No → エッジなし。待ちは無駄。並べて走らせる

データが渡らない2つの箱は独立。  
その独立性をこのガイド全体で利用する。

「AしてからBしてからC」はすでにグラフだ。  
ただ一番悲しい形（単一チェーン）で、Cが止まったらDは永遠に始まらない。

## Step 2 - 最初のグラフを作る（最初から最後まで）

準備：
- Claude Code v2.1.154+
- 有料プラン（Max/Team/EnterpriseはデフォルトON、Proは /config でDynamic workflowsをON）

手順：
1. 知っているリポジトリを開く
2. 以下のようなプロンプトを貼る（Anthropic公式ではない）  
   （src/routes/ を自分のパスに差し替え。「max 20」で最初は安く抑える）
3. 「workflow」が光るのを確認 → 「Dynamic workflow requested」と出たらグラフが作られている
4. 計画を承認する（ClaudeがJSオーケストレーションスクリプトとフェーズを書く）
5. 艦隊を走らせる（1ファイル1エージェント並列。セッションは空いている）  
   /workflows でライブ監視
6. 1つの答えを読む（20個の別チャットではなく、中間結果がスクリプト変数に残るから1レポートになる）

これでグラフが完成。1文から十数エージェントが動く。

### 「ゼロトークン」の話について
調整スクリプトはコードなので、エージェント間の結果渡しはチャット引き継ぎほどコンテキストを食わない。  
ただしエージェント自体の使用量はかかる。ワークフローは通常セッションより明らかに高い。  
節約は「調整」の部分だけ。最初はスコープを狭くして様子を見る。

良い結果が出たら「s」を押すと ~/.claude/workflows に保存され、名前で再実行できる。

### スケールの上限
1回のワークフローで最大1,000エージェントまで展開可能（同時稼働は最大16）。  
「1ウィンドウで1000+ループ」は比喩ではなく機能の実天井。

千のエージェント＝1つのコンテキストでは絶対に収まらない仕事（コードベース全体の監査、全ファイルに触る移行、千の角度での並列検索）ができる。

## Step 3 - 実際に壊れるところ

### 失敗1：グラフが自分に同意する
エージェントが自分の仕事をチェックすると甘くなる。  
モデルは自分の出力を好む。

対策：エッジに**独立したVerifier**を置く。  
ただしVerifierには「きれいなコンテキスト」が必要。  
実行者と同じ会話を渡すと、それは検証ではなく「別フォントでの自己同意」になる。

共有コンテキストのエージェント群は、ただの「ループの変装」だ。

### 失敗2：エージェントが互いに踏みつける
Bunチームが大規模ポートを並列で走らせた際、共有gitコマンドで上書きし合い失敗した。

対策は構造的：
- 危険なコマンドを禁止
- 各グループに独立したworktreeを与える

並列化する前に答える3つの質問：
1. 各エージェントはどこで作業するか？
2. 結果はどうマージするか？
3. 2つが意見が割れたらどうするか？

この計画がないグラフはスケールしない。ただ速く壊れるだけ。

## Step 4 - 今週作るべき6つのグラフ

方法：本物のエッジを見つける → ファンアウト → 独立コンテキストで検証 → 作業者を隔離

同じ形を違う仕事に当てはめるだけ：
1. **Security sweep**（ファイルごとにauth漏れを探す＋Verifier）
2. **Cited report with /deep-research**（質問を角度に分割し並列検索、互いに反証）
3. **Port a module**（ファイル単位＋テストをゲート＋失敗をループバック）
4. **Adversarial diff review**（サイズでルーティング：小変更は1パス、大変更は並列監査）
5. **Scheduled ecosystem scan**（一度保存して名前で再実行）
6. **Discovery of unknown size**（発見者が並列走行し、既知に対してチェック、2ラウンド新規がなければ停止）

### 天井の実例
BunのZig→Rustポートがこの仕組みで動いた：
- 約50ワークフロー
- ピーク64エージェント並列
- 約53.5万行のZigを100万行超のRustに
- 11日間
- 使用料約16.5万ドル
- 人間による設計と監視が必要
- 「これだけAIが書いたコードを安全にレビューできるか」という批判も出た

スケールは本物。価格と監督も本物。

## Step 5 - グラフを正直に保つアンカー

トポロジーだけでは真実は買えない。  
エージェントが互いに確認し合い、誰も現実に触れないネットワークは、単一ループと同じ失敗をする（ただ部品が増えるだけ）。

必要なのは「議論できないアンカー」：
- 実際に走ったテスト（「通るはず」ではなく「通った」）
- 証拠に基づくVerifier（雰囲気ではなく）
- エージェントが決して調整できない凍結ルール（最適化が弱めたいものこそ守る）

グラフの誠実さは「動かないもの」の強さで決まる。

### グラフが間違った選択になるとき
ほとんどのタスクはグラフではない。不要なのに使うと金を燃やし失敗の道を増やすだけ。

スキップすべき場合：
- タスクが小さく孤立している（関数追加・バグ1個修正）
- すべてのステップを読んで承認したい（グラフの「あなたなしで広く走る」という目的と逆）
- 何を探しているかまだ分からない（探索は1エージェントを操縦する方が良い）
- ステップが本当に依存し合っている（本当のチェーンなら並列の余地がない）

判断の目安はStep 1：  
2つの箱の間に矢印が1本も見つからないなら、グラフは存在しない。ループで十分。

グラフは「幅」のための道具。  
作業が広くないなら、線は最初から問題ではなかった。

---

## 最後のシフト
プロンプターは質問する。  
アーキテクトはグラフを描く。

線形エージェントは天井ではなかった。  
ただ「最初の形」だっただけ（1行ずつ打つ人間の思考に合っていたから）。

ノードとエッジが見えるようになれば、  
「エージェントにもっとやれ」ではなく  
「グラフにもっと広くやれ」と頼むようになる：

- 独立した仕事はファンアウト
- 信頼が重要なところはエッジにゲート
- 真実を守るノードは凍結

ほとんどの人は線にステップを並べ続ける。  
グラフを描き、壊れるところを理解した少数が艦隊を動かす。

**グラフを描け。アーキテクトであれ。**
