# コピペで使える CLAUDE.md テンプレート集  （2,000時間の試行錯誤から見えた設計指針）

## はじめに

「CLAUDE.mdにルールを書いたのに、全然守ってくれない」 「/initで生成したCLAUDE.md、これで合っているのか分からない」 「出力がイマイチだけど、どこを直せばいいのか分からない」

そんな悩みを持つ人に向けて、2,000時間以上Claude Codeを使い込んで辿り着いたルール設計の考え方と、そのままコピペで使えるテンプレート4種を紹介します。

ほとんどの人のCLAUDE.mdはクオリティが低いのが実情です。問題は「何を書いたか」ではなく、「書き方の設計」そのものが根本的に間違っていることにあります。

## 1. なぜCLAUDE.mdは機能しないのか

### 「CLAUDE.mdに全部書け」という思い込み

多くのCLAUDE.md解説記事は「書けば書くほど強くなる」と言いますが、これは半分正しく半分間違いです。

Claude Codeには、指示を伝えるための仕組みが実は7つあります。CLAUDE.mdはそのうちの1つに過ぎません。

- CLAUDE.md
- .claude/rules/
- Skills
- Subagents
- Hooks
- Output Styles
- System Prompt

この7つを適材適所で使い分けることが重要です。

しかもCLAUDE.mdは「ガイダンス」であって「命令」ではありません。100%守られる保証はどこにもないのです。

全部をCLAUDE.mdに詰め込むのは、全社員宛のメールで1人にしか関係ない連絡をするようなもの。ノイズだらけになり、本当に大事なルールが埋もれてしまいます。

CLAUDE.mdに書くべきは「全セッションで必要な情報だけ」——これが大前提です。

### /initで自動生成したCLAUDE.mdはそのまま使わない

/initはClaude Codeが自動でCLAUDE.mdの雛形を生成してくれる公式機能ですが、そのまま使うのはおすすめできません。

HumanLayerのブログでは、「CLAUDE.mdはAIチームメイトとの最も高レバレッジなポイントであり、それを自動生成に任せるのは、採用面接の質問をAIに丸投げするようなものだ」と指摘されています。

/initで生成される内容は、多くの場合「良いコードを書いてください」といった一般論や冗長な言い回しに終始し、プロジェクト固有の知識がほとんど含まれていません。これでは出力の質が上がるはずがありません。

よくある失敗パターンと、その結果は以下の通りです。

- 冗長な表現の繰り返し → 処理速度の低下
- 不要な例外処理を大量に列挙 → 通常の質問にすら答えにくくなる
- 「あなたはAIアシスタントです」といった自己紹介 → AIは自分が何者か既に知っている
- 具体例を20〜30個並べる → かえって応用が効かなくなる
- API仕様を丸ごとコピペ → 実際に使うのは一部のエンドポイントだけ
- 出力形式を細かく20行で規定 → 「Markdown形式で」の1行で十分
- 人格設定に数百字を費やす → 回答品質がむしろ下がる

/initの出力は「スタート地点」ではなく、「一度捨てるべき下書き」と考えた方がよいでしょう。

### CLAUDE.mdが「無視される」3つの原因

「書いたのに守られない」のは、バグではなく仕様です。原因は主に3つあります。

**原因①: ファイルが長すぎる** Anthropic公式は、200行を超えると重要なルールがノイズに埋もれて無視される確率が上がると明言しています。500行を超えるのは論外です。

**原因②: 表現が曖昧** 「きれいなコードを書いて」では解釈の幅が広すぎます。AIは「きれい」の定義が分からないため、独自の解釈で書いてしまいます。 例:「フォーマットする」→「2スペースインデント、セミコロンなし、シングルクォート」のように、具体的な制約に落とし込むことで初めて遵守されます。抽象的な希望は無視されがちです。

**原因③: CLAUDE.mdの役割の誤解** CLAUDE.mdはシステムプロンプトではなく、「お願い」レベルのガイダンスです。100%守らせたいルールには、後述するHooksが必要になります。

「書いたのに守られない」問題は、設計を見直すことで解決できます。

## 2. 「削るほど強くなる」設計思想

### 「この行を消してAIが間違えるか?」で判断する

Anthropic公式が示すCLAUDE.md設計の核心はこうです。

「各行について問いかけよう。この行を削除したら、Claudeは間違いを犯すか? ——答えがNoなら削るべきだ」

Claude Code開発者のBoris氏が使っているCLAUDE.mdは約100行。コミュニティ調査(HumanLayer調べ)では最適値は60行前後とされ、Anthropic公式も200行以下を推奨しています。

LLMの注意力は人間と同じで、長くなるほど集中力が落ちます。500行以上あったCLAUDE.mdを150行まで削った結果、遵守率が目に見えて上がったという実例もあります。冗長な表現を統一するだけで処理速度が改善し、自明な記述を削るだけで大幅に短縮できることも珍しくありません。

最強のCLAUDE.mdとは「何も書かない」ことではなく、「必要なことだけ書く」こと。この引き算の発想が鍵になります。

### 7つのメカニズムを使い分ける

Claude Codeの指示メカニズムは以下の7つに整理できます。CLAUDE.md以外の6つを知っているだけで、設計の自由度が大きく広がります。

|メカニズム|ロードタイミング|コスト|向いている用途|
|---|---|---|---|
|CLAUDE.md|常時ロード|高|ビルドコマンド・ディレクトリ構成|
|.claude/rules/|パスマッチで発動|中|ファイル固有の制約|
|Skills(.claude/skills/)|名前だけ常時表示、本体はオンデマンド|低|手順書・チェックリスト|
|Subagents(.claude/agents/)|呼び出し時のみロード|低|コード検索・レビュー|
|Hooks|イベント駆動|—|Lint強制・危険コマンドのブロック(100%強制)|
|Output Styles|セッション開始時|—|ロール変更|
|System Prompt追加|CLI起動時のみ|—|トーン・フォーマット指定|

判断基準はシンプルです。

- 「100%守らせたい」→ Hooks(CLAUDE.mdではない)
- 「特定パスのファイル操作時だけ」→ Path-scoped rules
- 「30行以上の手順書」→ Skills(常時ロードのコストを回避)
- 「毎セッション必要」→ CLAUDE.md

LLMが安定して守れる指示の上限は150〜200個程度と言われており、システムプロンプトだけで約50個を消費するため、CLAUDE.mdに残る「予算」は100〜150個程度です。この予算を7つのメカニズムに適切に配分することが設計の肝になります。

「どこに書くか」の判断は、「何を書くか」と同じくらい、あるいはそれ以上に重要です。

## 3. コピペで使えるテンプレート4選

### テンプレ①: グローバルCLAUDE.md — 全プロジェクト共通の「自分ルール」

`~/.claude/CLAUDE.md` に置くと、どのプロジェクトでも自動的に読み込まれます。

```markdown
# グローバル設定

- 簡潔に回答。前置き不要
- 判断に迷う場合のみ質問。それ以外は自分で判断して進める
- rmよりtrashを優先
- 外部への送信(メール、ツイート)は確認してから実行
- タスク完了したら結果を報告(何をやったか、成果物はどこか)
- 日本語で回答

## 作業スタイル
- 全体設計してから手を動かす
- 一括処理の前に2-3件でテスト
- 「待って」「止めて」→ 即座に作業停止
```

わずか15行ですが、「この行を消してAIが間違えるか?」というテストを通過した行だけを残した結果です。

ポイントは「自分の作業スタイル」と「安全ルール」だけを書くこと。技術的な内容はプロジェクトCLAUDE.mdに任せ、ここには「自分がどういう人間で、どう仕事を進めたいか」だけを書きます。

### テンプレ②: プロジェクトCLAUDE.md — 60行で最大効果を出す構成

プロジェクトルートに置く `./CLAUDE.md` です。

```markdown
# プロジェクト名

## プロジェクト概要
2-3行でプロジェクトの説明。技術スタック: Next.js 14 / TypeScript 5.4 / Prisma

## ディレクトリ構成
src/
├── app/          # Next.js App Router
├── components/   # UIコンポーネント
├── lib/          # ユーティリティ
└── types/        # 型定義

## 開発コマンド
- テスト: npm run test:unit
- ビルド: npm run build
- Lint: npm run lint

## 絶対ルール(IMPORTANT)
- any型の使用禁止。unknownを使う
- 変更は依頼範囲に限定。隣接コードの改善は許可なくやらない
- 大きな変更の前に計画を説明し、承認を得てから実装する

## よくあるハマりポイント
- prisma generateを忘れるとビルドが通らない
- 環境変数DATABASE_URLが必要(.env.localに設定)

## Off-Limits(触るな)
- src/legacy/ — 移行予定だがまだ稼働中。触らない
```

6セクション、約60行。「AIが推測できないこと」だけに絞った最小構成です。

実践上のコツは2つあります。

1. 「IMPORTANT」や「YOU MUST」をセクション名に入れると遵守率が上がります。Anthropic公式が推奨しているテクニックです。
2. テストコマンドを1行書くだけで、「テストはどう走らせますか?」という毎セッションの無駄なやり取りがなくなります。公式もこれを「CLAUDE.mdで最もROIが高い1行」と位置づけています。

### テンプレ③: .claude/rules/ — 必要なときだけ発動する条件付きルール

CLAUDE.mdに全部書くと膨れ上がりますが、ルール自体は必要です。その解決策が `.claude/rules/` です。

YAMLフロントマターで「どのファイルを触ったときに発動するか」を指定できます。

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "**/*.test.ts"
---
# API開発ルール
- 全エンドポイントでZodバリデーション必須
- レスポンス形式: { data, error, meta }
```

`src/api/` のファイルを触ったときだけこのルールが自動で読み込まれ、それ以外のフォルダを触っているときはロードされません。コンテキストの無駄遣いがなくなります。

CLAUDE.mdからrules/へ移すべきものの判断基準の例:

- APIバリデーション → `.claude/rules/api-guidelines.md`(`src/api/**/*`)
- Reactコンポーネント規約 → `.claude/rules/react-patterns.md`(`src/components/**/*`)
- テストの書き方 → `.claude/rules/testing-rules.md`(`**/*.test.*`)
- セキュリティ → `.claude/rules/security.md`(`src/auth/**/*`)

ルールを20ファイル以上に分割して管理すれば、CLAUDE.md本体を150行程度に収めることも可能です。基準はシンプルで、「常に必要 → CLAUDE.md、条件付き → rules/」です。

### テンプレ④: Hooks — CLAUDE.mdでは守れないことを100%強制する

CLAUDE.mdは「お願い」、Hooksは「強制」。この違いを理解していないケースが多く見られます。

「rm -rfは使うな」とCLAUDE.mdに書いても、それだけでは確実にブロックできません。100%止めたいならHooksを使います。以下、実戦的な設定例を3つ紹介します。

**設定①: 危険コマンドのブロック**

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "script": "if echo \"$TOOL_INPUT\" | grep -qE 'rm -rf|git push --force|drop table'; then echo 'BLOCKED' >&2; exit 2; fi"
    }]
  }
}
```

**設定②: 自動フォーマット**

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "script": "npx prettier --write \"$TOOL_INPUT_FILE\" 2>/dev/null || true"
    }]
  }
}
```

**設定③: コミット前のLintゲート**

```json
{
  "hooks": {
    "Stop": [{
      "script": "npm run lint -- --quiet; if [ $? -ne 0 ]; then echo 'Lint errors found' >&2; exit 2; fi"
    }]
  }
}
```

判断基準はシンプルです。「ルール破りで取り返しのつかない事故が起きるか?」——Yesなら Hooks、Noなら CLAUDE.md。

テンプレ①〜③で「伝える」、テンプレ④で「守らせる」。この組み合わせが実践的な完成形です。

## まとめ

CLAUDE.mdは「書くもの」ではなく「削って育てるもの」です。今日から始められるアクションは次の5つです。

1. /initで生成したCLAUDE.mdを一度リセットする
2. テンプレ①②をコピペし、自分のプロジェクト情報に書き換える
3. CLAUDE.mdが200行を超えたら `.claude/rules/` に分割する
4. 「100%守らせたいルール」はHooksに移す
5. 週1回、「この行を消してAIが間違えるか?」というテストで見直す

出典元の記事では、CLAUDE.mdの整備により個人のPR数が+98%、生産性が+20〜50%向上したというAnthropic社内データが紹介されています(数値は元記事からの引用で、当方では未検証です)。この5つのアクションを実践するだけでも、Claude Codeの出力品質は大きく変わるはずです。
