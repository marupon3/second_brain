エージェントのループとワークフローアーキテクチャについて少し勉強したところ、予想以上に明確になったことがあります。ループエンジニアリングとグラフエンジニアリングは、しばしば競合するアプローチのように語られますが、実際には異なる問題を解決しています。ループは「実行を続けるべきかどうか」を制御し、グラフは「次にどこへ実行を移すべきか」を制御します。

## ループエンジニアリングが実際に制御するもの

ループエンジニアリングは、測定可能な条件が満たされるまで繰り返し実行することを中心に構築されています。

### 基本的なループには通常、次の5つの段階があります：
- 何をする必要があるかを発見する
- 次に有用なアクションを計画する
- 必要な作業を実行する
- 明確な条件に対して結果を検証する
- 結果がまだ失敗している場合は反復する

この構造により、ループはタスクに何回の試行が必要か事前にわからない場合に特に有用です。すべてのループの背後にある核心的な質問は次の通りです：  
システムはもう一度反復を実行すべきか？

## グラフエンジニアリングが制御するもの

グラフエンジニアリングは、同じ結果を繰り返し改善するのではなく、実行が複数の異なるパスを通る可能性がある場合に有用になります。研究エージェントは例えば、research → verify → write → review → publish と進み、失敗時には完全に異なる以前の状態へ実行をルーティングできます。
### グラフエンジニアリングは、システムが次のようなものを必要とするときに有用です：

- 複数の可能な実行パス
- 異なる状態間の明示的な遷移
- 現在の結果に基づく条件分岐
- 独立して実行可能な並列ステージ
- 完了したワークフローのための明確な終了状態

すべてのグラフの背後にある核心的な質問は次の通りです：  
ここから実行はどこへ移るべきか？

両者の責任を分けると、区別がずっと明確になります。ループは繰り返しを管理し、グラフは方向を管理します。

### 本番エージェントは通常両方を必要とする
興味深いのは、両方の構造が一緒に動作するときです。グラフが全体のワークフローを定義し、個々のノードが自身の完了条件に向けて繰り返し作業するループを含むことができます。

したがって、本番エージェントには例えば次のようなものが含まれる可能性があります：
- 十分な証拠を集める研究ループ
- 矛盾する情報を解決する検証ループ
- 弱い部分を改善する執筆ループ
- すべてのステージをつなぐグラフ

グラフはどのステージがアクティブになるかを決定し、各ループは現在のステージがもう一度試行を必要とするかどうかを決定します。

| Layer    | Main responsibility                             |
| -------- | ----------------------------------------------- |
| Graph    | Decides where execution can move next           |
| Loop     | Decides whether execution should continue       |
| Model    | Performs the work inside each step              |
| Verifier | Checks whether the result meets the requirement |

これらの責任が分離されると、モデルはエージェント全体ではなくなります。  
より大きな実行システムの中の一つのコンポーネントになります。

## より大きなシフト

有用な比較は、本当にループエンジニアリングかグラフエンジニアリングかを選ぶことではありません。ループエンジニアリングは、もう一度の試行が正当化されるときにエージェントが作業を続ける方法を与え、グラフエンジニアリングは、現在の状態が異なるものを必要とするときにエージェントが方向を変える方法を与えます。

私が見つけた最もシンプルな区別はこれです：
- ループは試行をまたいだ繰り返しを制御する
- グラフは状態をまたいだ方向を制御する
- モデルはそれらの構造の中で作業を実行する
- 検証器は結果が許容可能かどうかを決定する

グラフは実行がどこへ行けるかを決定し、ループは実行を続けるべきかどうかを決定します。この区別により、エージェントアーキテクチャについて考えるのがずっと簡単になりました。
