# 1. 要約

Claude Codeで自作エージェントを使っている人向けの速報。
Anthropic公式が「AI利用料を約1/13に抑える手順書」を無料公開したと紹介。

主なポイントは次の4つ：
- 先に「合格ライン」を決める（品質を落とさない前提を作る）
- **同じ前置きを毎回送り直さない（1回分の料金で使い回す）** ← これが特に効果大で、1件あたりの料金がほぼ半分になった
- 資料は最初に全部渡さず、必要になったときだけ取りに行かせる
- 返事の形式を先に指定して、長い出力自体を短くする

特に2つ目の「前置きの再利用」が最も効いた、という内容です。

# 2. 前置き再利用の具体例


AnthropicのClaudeでは、**同じ前置き（system prompt + ツール定義 + 固定コンテキスト）を毎回送り直さず、キャッシュして再利用**できます。  
キャッシュされた部分は**通常の入力料金の約1/10**で済みます（キャッシュヒット時）。

### 基本の仕組み
1. 最初のリクエストで「静的な前置き」を送る → キャッシュに書き込み（少し高い料金）
2. 2回目以降、**まったく同じ前置き**から始まるリクエストを送る → キャッシュから読み取り（約1/10の料金）
3. 
前置きは**先頭から順番に一致**しないとキャッシュが効きません。  
そのため「静的なものを先に、動的なものを後ろに」配置するのが鉄則です。

### 具体例1：Claude Code風のエージェント構成

**毎回送る前置きの構成（推奨順）**
1. 静的なシステムプロンプト（役割・ルール・出力形式など）
2. ツール定義（tools）
3. CLAUDE.md やプロジェクト固有の知識
4. セッション共通のコンテキスト
5. 会話履歴（messages）← ここから動的に増える

**悪い例（キャッシュが毎回壊れる）**
システムプロンプトの中に「現在の日時：2026-08-19 05:44」を入れる
→ 時間が変わるたびに前置き全体が変わってしまい、キャッシュ無効

**良い例（メッセージで渡す）**
システムプロンプトは固定のまま。
必要になったら user メッセージの中に
「現在の日時は 2026-08-19 05:44 です」と入れる。
→ 前置きは変わらないのでキャッシュが効き続ける

### 具体例2：APIでの書き方（Pythonイメージ）

# 最初のリクエスト（キャッシュ書き込み）
response = client.messages.create(
    model="claude-sonnet-4-...",
    system=[
        {
            "type": "text",
            "text": """あなたは優秀なコーディングエージェントです。
以下のルールを厳守してください：
- コードは必ず実行可能な状態で返す
- 説明は簡潔に
- ...（長い固定の前置き）""",
            "cache_control": {"type": "ephemeral"}  # ここまでをキャッシュ
        }
    ],
    messages=[{"role": "user", "content": "このファイルを修正して"}]
)

# 2回目以降（同じ system を送るとキャッシュヒット）

# → 前置き部分の料金が約1/10になる

### 実際の効果イメージ
- 前置きが 10,000トークンある場合  
- 毎回フル料金で送る → 高い  
- キャッシュを使う → 初回だけ少し高く、2回目以降は **ほぼ半分以下** になることが多い

Claude Codeの公式でも「いちばん効いたのはこの前置きの再利用」とされており、  
エージェントを自作している人ほど効果が大きくなります。


# 3. CLAUDE.mdのキャッシュ最適化

Claude Codeでは `CLAUDE.md` は**プロジェクトコンテキスト層**として扱われ、セッション内でキャッシュされます。  
同じ内容が続く限り、2回目以降は約1/10の料金で再利用されます。

### 1. キャッシュが効く仕組み（位置づけ）
Claude Codeのリクエストはだいたいこの順で組み立てられます：
1. **System prompt + Tools**（グローバルにキャッシュ）
2. **CLAUDE.md**（プロジェクト内でキャッシュ）
3. **Session context / Conversation**（会話が増える部分）
4. 
`CLAUDE.md` はシステムプロンプトに直接埋め込まず、`` としてメッセージの先頭に注入される設計です。 
これにより「全ユーザー共通のsystem promptキャッシュ」を壊さずに、プロジェクト固有の内容だけを独立してキャッシュできます。

### 2. キャッシュを最大化する書き方
| やるべきこと | 理由 |
|--------------|------|

| **短く・信号密度高く**（目安200行以下、できれば60〜100行） | 毎回コンテキストに乗る。長いとノイズが増え、キャッシュ後もコンテキスト圧迫 |

| **静的な内容だけ書く** | 日時・UUID・一時的な作業メモを入れない。変わるとキャッシュが無効になる |

| **よく使うコマンドを具体的に書く** | 例：`npx vitest run  --reporter=dot`。出力が短くなり、後続のコンテキストも軽くなる |

| **ワークフロー固有のものはSkillsに逃がす** | 毎回使う必要のない指示はSkillsに移すと、CLAUDE.mdが安定する |

| **セッション開始前に確定させる** | 途中で編集すると、次回の `/clear` や `/compact` かセッション再起動まで反映されない（キャッシュ自体は維持されるが、古い版が使われ続ける） |

### 3. キャッシュを壊しやすいNG行動
- **セッション中にCLAUDE.mdを編集する**  
  → 編集自体はすぐにキャッシュを壊さないが、内容が反映されず、次のセッションでフル料金になる

- 日時や動的な値を入れる
- モデルやeffort levelを途中で切り替える（キャッシュがモデルごとに分かれる）
- 不要なMCPサーバーを常時ONのままにする（`/mcp` でオフにできる）

### 4. 実践的な最適化手順
1. **セッション開始直後に `/context` を実行**  
   今ロードされているCLAUDE.mdやツール定義の量を確認する
2. **不要な行を削る**  
   「これ本当に毎回必要？」という行を削除 or Skillsに移動
3. **テスト・ビルドコマンドを短くする指示を入れる**  
   例：
   ## Commands
   - テスト: `npx vitest run  --reporter=dot`
   - ビルド: `pnpm build`（詳細ログ不要）

1. **作業が区切れたら `/clear`**  
   前のタスクのノイズを消して、次のタスクでクリーンなキャッシュを使う

2. **長時間空ける前に `/compact`**  
   キャッシュがまだ温かい間に圧縮すると、コストが抑えられる

### 5. 効果の目安
- 初回リクエスト：CLAUDE.md分をフル料金で書き込み
- 2回目以降（5分以内、同じ内容）：約1/10の料金
- セッション全体でCLAUDE.mdが長めでも、**「1回分の料金 + あとはほぼ無料」** に近づく

要するに、**CLAUDE.mdは「短く・静的・確定的」に保つ**のがキャッシュ最適化の本質です。  
動的な情報や一時的な指示はメッセージやSkills側に逃がすのがコツです。

# 4. SkillsとCLAUDE.mdの役割分担

シンプルに言うと：
| 項目 | CLAUDE.md | Skills |
|------|-----------|--------|
| **役割** | Claudeが**常に知っているべき事実・ルール** | Claudeが**必要なときだけ使う手順・知識** |
| **読み込み** | セッション開始時に**毎回・全量** | 名前＋説明だけ常時（約100トークン）、**本体は必要時のみ** |
| **トークンコスト** | 常にコンテキストを消費 | 使わない限りほぼゼロ |
| **向いているもの** | 「いつも守る」もの | 「この作業のときだけ」のもの |
| **強制力** | 助言（Claudeが無視する可能性あり） | 助言（同様） |

### CLAUDE.md に書くべきもの
**「このプロジェクトでClaudeが毎回知っておくべきこと」**
- プロジェクト概要・アーキテクチャの要点
- 技術スタック・パッケージマネージャー（例：pnpmを使う、npmは使わない）
- 共通のコーディング規約・命名規則
- よく使うビルド・テストコマンド（例：`npx vitest run  --reporter=dot`）
- 「絶対にやってはいけないこと」（例：mainに直接pushしない）
- ディレクトリ構成のざっくりした地図

**目安**：200行以下（できれば60〜100行程度）。短く・信号密度高く保つ。

### Skills に書くべきもの

**「特定のタスクで繰り返し使う手順や詳細知識」**
- デプロイ手順・リリースチェックリスト
- コードレビューの観点・PR作成フロー
- データベースマイグレーションの手順
- APIスタイルガイドや詳細なドキュメント
- 「同じ指示を何度も貼り付けている」作業  

Skillsは `.claude/skills/`（プロジェクト）や `~/.claude/skills/`（個人）に置き、`SKILL.md` というファイルで管理します。  

Claudeが自動で判断して読み込むか、`/skill-name` で明示的に呼べます。

### 判断のコツ（公式の目安）
- **事実・常時ルール** → CLAUDE.md  
  例：「このリポジトリはpnpmを使う」「テストはファイルの隣に置く」

- **手順・プレイブック** → Skills  
  例：「デプロイするときはこの7ステップで進める」「PRレビューはこのチェックリストでやる」

**CLAUDE.mdの中に「手順っぽい長いセクション」が増えてきたら、それはSkillsに移すサイン**です。  
そうすることでCLAUDE.mdが軽く保たれ、キャッシュ効率も上がり、コンテキストも汚れにくくなります。


### 組み合わせ例
CLAUDE.md（常時）
- プロジェクト概要
- 「pnpmを使う」
- 「テストは --reporter=dot で実行」
- 「API規約はスキルに従う
- 
Skill: api-conventions（必要時）
- 詳細なAPI設計ルール
- エンドポイント命名例
- エラーハンドリングの書き方

Skill: deploy（必要時 or /deploy）
- デプロイ前チェックリスト
- 本番反映手順

この分担を意識すると、  
**常時コンテキストは軽く・必要な知識は必要なときだけ**という理想的な状態になります。
