# エージェントメモリ設計

AIエージェントが「セッションをまたぐと過去の会話を一切覚えておらず、毎回ゼロから始まる」問題に対して、記憶を永続的に保存・検索可能にする設計論。[[Claude_Code徹底ガイド]]の「メモリエンジニアリング」節（保存/取り出し/削除の7ステップ）とは別ソースの、より広いアーキテクチャ視点でのまとめ。

## Working Memory と Long Term Memory を分けるべき理由

一時的なメモ（スクラッチノート）と永続的な検証済みの事実を混ぜると、将来の実行を汚染する。

- **Working Memory**: 今のタスク専用の一時的・容量制限付きの作業空間。
- **Long Term Memory**: 事実・知識・スキルを蓄える永続的な知識ベース。

**メモリ分離のチートシート**:
1. Working Memoryは1つのタスクに限定する
2. 検証済みの事実だけをLong Term Memoryに昇格させる
3. ツールの生出力をそのままLong Term Memoryに入れない
4. Long Term Memoryからの取得は関連度スコアを使う
5. タスク終了時にWorking Memoryをクリアする
6. 昇格内容を定期的にレビューする

核心の原則は「一時的なノイズを永久的な知識にしてはいけない」こと。昇格（Promote）は偶然ではなく明示的な書き込みで行い、取得（Retrieve）・削除（Expire）と合わせた3操作で管理する。

## LLM推論がステートレスであることの構造的な問題

LLM推論は本質的にステートレス（1回の入力→1回の出力で、モデル自体は変化せず対話内容を保持しない）。これは再現性・単純さという利点がある一方、次の課題を生む。

- **計算の非効率**: 毎回同じような計算をゼロからやり直す。
- **コンテキストウィンドウの限界**: 長い会話やエージェント的ワークフローでは履歴全体を毎回プロンプトに再投入する必要があり、コンテキストが伸びるほど「Context Rot（文脈の劣化）」と注意誤りが起き、KVキャッシュの計算コストも膨らむ。
- **推論をまたいだ長期学習ができない**: 再学習なしにデプロイ経験から自己改善できない。
- **エージェント同士が孤立する**: エージェント間で知識を共有する仕組みがない。
- **知識ベースが蓄積しない**: 推論から得られた知識・記憶が積み上がらない。

コンテキストの圧縮・フィルタリング・RAG・キャッシュといったContext Engineering技術はこれらの症状を緩和するが、根本原因（推論のステートレス性そのもの）は解決しない。エージェントメモリはこの根本原因に対応する、より基本的な解決策として位置づけられる。

## メモリの分類

- **クライアント側 vs サーバー側**: クライアント側メモリはエージェント個人に閉じたもの（例: 個人用アシスタントが作るメモリ）。サーバー側メモリはプロバイダー管理で、複数エージェント間の学習・企業のデータガバナンス・監査・バージョニング・出典管理などを備える。
- **メモリの種類**（用語はまだ流動的）:
  - **セッションメモリ**: 1回のエージェント⇔LLMセッション内の会話履歴全体。寿命はそのセッション限り。
  - **長期ファイルシステムメモリ**: ファイルとして保存される記憶（補助的なインデックス付きのことも）。エージェントのランタイムがディレクトリ構造を自然に辿れるため有効。本Vaultの`wiki/`もこの形に近い。
  - **長期エピソード記憶**: 出来事や時系列に沿って構造化された永続的記憶。セッションを超えて残る。
  - **長期意味記憶**: 埋め込み（エンベディング）で保存され意味検索・取得できる永続的記憶。典型的にはグラフメタデータ・インデックス付きのベクトルDBで実装される。

## サンプルのEnd-to-Endアーキテクチャ

複数種のエージェント（LangGraphのようなワークフロー型、OpenClawのような永続エージェント）が共有メモリ基盤を介してLLMとやり取りする構成の要点。

1. **プロンプト組み立て**: セッションメモリ・RAGで取り込んだデータ（VectorDB/GraphDB）・長期メモリ・企業のデータストアからコンテキストを集約する専用の関数を、モデルごとに持つ。
2. **推論**: 組み立てたプロンプトを選択したLLMへ送る。
3. **メモリの書き戻し**: 推論後、新しい記憶を長期メモリへ書き戻す。クライアント⇔LLM間のやり取りを透過的に横取りする暗黙的な方式と、クエリ応答のたびに明示的なメモリツール/スキルで書き込む方式がある。
4. **階層的なメモリ構造**: エージェント個別スコープの長期メモリ（Agent1のLTM、Agent2のLTM）と、チーム/組織全体で共有する長期メモリの2層。個人化と集団学習の両方を可能にする。新しく参加した人間・エージェントがチームの暗黙知にすぐアクセスできる、個人の離脱によるナレッジ損失が減る、といった「企業マインド」的な効果が期待されている。
5. **データ分離**: エージェントメモリは企業の正データ（source of truth）とは別に保たれ、エージェントメモリ操作によって正データが書き換わることはない。
6. **バックグラウンドでのメモリ整備（Dreaming）**: 重複削減・陳腐化した記憶の失効・新しい記憶同士の関連付け・新知識の導出を継続的に行うプロセス。一部のフレームワークでは「Dreaming」と呼ばれる。

## 主なオープンソース・製品動向（2026-08時点）

- **Mem0**: 会話から有用な情報を自動抽出・整理し、セッションをまたいで将来のプロンプトに再注入するメモリレイヤー。長期会話のベンチマーク（LoCoMo等）で良好な結果を主張。ローカルデプロイのプラグインとしてもクラウド版としても使える。
- **OpenClaw**: 組み込みのファイルベースメモリ（`MEMORY.md`に恒久的な事実、`memory/YYYY-MM-DD.md`に日次メモ）を持ち、`memory_search`/`memory_get`でキーワード・ベクトル検索する。会話の圧縮前に重要情報を保存する「メモリフラッシュ」パスと、短期メモを高シグナルな長期メモリに統合する任意の「Dreaming」パイプラインを備える。外部メモリプロバイダー（Mem0等）をプラグインとして差し込むこともできる。
- **Claude Code等のコーディングエージェント**: CLAUDE.mdは「最も素朴な形のエージェントメモリ」と位置づけられる。リポジトリ構造・過去のデバッグ試行・コーディングの好み・セッションをまたぐ長期タスクを覚える必要があるため、メモリ設計の重要性が特に高い領域。
- **Karpathyの「LLM-Wiki」系プロジェクト群**: 生データを取り込み「コンパイル」してリンク済みのwiki形式の記憶ベースにする発想（詳細は[[セカンドブレインはストレージではなくコンパイラ]]）。Graphify・Graphitiはこれをより構造化されたグラフDB寄りに発展させたもの。他にagentmemory・OpenViking・MemoryHub・Zep/Graphiti・Honcho等が同じ課題に別のアプローチで取り組んでいる。

## 実験: メモリの有無で何が変わるか

同一の2セッションタスク（「無料の天気APIを調べてBeaconというプロジェクトに推薦し、次のセッションで続きから再開する」）を、標準のOpenClaw（ファイルベースメモリのみ）とMem0プラグイン併用で比較。

- **セッション1**は両者とも同一（Open-Meteoを推薦）。
- **セッション2**: 標準設定は「Beaconプロジェクトの記録がない、初対面のようだ」と回答。Mem0併用では即座に文脈を復元し、プロジェクトの雛形作成・実際のAPI呼び出しまで自律的に継続した。

エージェントは技術的にはメモリを保存できる（テスト中も名前や好みなどの個人情報は保存していた）が、プロジェクトの詳細を保存すべき情報だと自律的に判断しなかった。1回のプロンプトの後で明示的なブリーフを見失うようなら、その判断の信頼性は長期の作業ではさらに下がっていく。専用のメモリ層はこのリスクを取り除く。
