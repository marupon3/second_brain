# グラフエンジニアリング

複数のAIエージェント（それぞれが独自のループを回す）を組み合わせたシステムを、単一ループのプロンプトチェーンではなく「有向グラフ」として設計する手法のメモ集。[[Claude_Code徹底ガイド]]の「エージェントをグラフとして設計する（Node/Edge思考）」の詳細版。

## 基本概念：ノードとエッジ

- **ノード（点）** = 作業の単位（1つのエージェント、1つのタスク、決定論的な関数、人間の承認ポイント）。
- **エッジ（矢印）** = 依存関係（「この出力を次の入力にする」というつながり。実行順そのものではない）。
- 「どの作業がどの作業の前に必要か」「どれとどれは同時に走らせられるか」を図で表したもの。
- 「プロンプターは質問する人」「アーキテクトはグラフを描く人」——エージェントに何をさせるかではなく、作業の構造（ノードとエッジ）をどう設計するかに焦点を移す考え方。

| 構造 | 特徴 | 限界 | 適した場面 |
| --- | --- | --- | --- |
| 単一エージェント（ループ） | 1つのエージェントがツールを繰り返し使う | 複雑タスクでコンテキスト溢れ、役割分担できない | 単純なタスク |
| 直線チェーン | A → B → C の順番実行 | 並列不可、依存関係が固定 | 順番が明確な処理 |
| グラフ | ノード＋エッジで自由な形状 | 設計が複雑になる可能性 | 分岐・並列・再試行・協調が必要なシステム |

## ループとグラフの責任分離

しばしば対立する手法のように語られるが、実際には解く問題が違う。

- **[[ループエンジニアリング|ループ]]が制御するもの**: 「実行を続けるべきかどうか」。測定可能な条件が満たされるまで、発見→計画→実行→検証→反復を繰り返す。核心の問い＝「システムはもう一度反復すべきか？」
- **グラフが制御するもの**: 「次にどこへ実行を移すべきか」。複数の実行パス・状態間の明示的な遷移・条件分岐・並列ステージ・明確な終了状態が必要なときに有用。核心の問い＝「ここから実行はどこへ移るべきか？」

本番エージェントは両方を必要とすることが多い。グラフが全体のワークフローを定義し、その中の各ノードが自身の完了条件に向けて繰り返し作業するループを持つ、という組み合わせ。グラフがどのステージをアクティブにするかを決め、各ループはそのステージが再試行を必要とするかを決める。

| レイヤー | 主な役割 |
| --- | --- |
| Graph | 次にどこへ実行を移せるかを決める |
| Loop | 実行を続けるべきかを決める |
| Model | 各ステップ内部で作業を行う |
| Verifier | 結果が要件を満たすかを判定する |

## 代表的な適用例

1. **ソフトウェア開発**（Boris Cherny / Claude Codeの典型例）: 独立した調査・修正エージェントをファンアウトで並列実行、依存関係をゲートで待たせる、変更後は「新鮮なコンテキスト」の別エージェントに検証させる。数百〜数千のエージェントを5〜20時間走らせ、人間はグラフの設計と監視に集中する運用も。
2. **カスタマーサポート・チケット処理**: チケット分類→注文データ照会（決定論的ツール呼び出し）→ビジネスルール適用→応答生成→自己レビュー・書き換え→根拠チェック（幻覚防止）→人間エスカレーション、というノード構成。分岐や合流、失敗時のフォールバックをエッジで定義する。AIノードと決定論的ノードを混ぜるのがポイント。
3. **研究・レポート作成（Map-Reduce系）**: Map（複数のリサーチエージェントを並列で走らせ、それぞれ異なる情報源を調査）→Reduce（結果を集約）→Verify（別エージェントが根拠を確認）→Synthesize（最終レポートをまとめる）。トーナメント方式（複数案を生成して比較）やエスカレーションラダー（簡単なケースは安価なモデル、難しいケースは高性能モデル）もよく使われる。
4. **業務フロー（請求書トラブル解決など）**: 請求書解析→ルールベース判定（決定論的）→AI判断→人間承認チェックポイント。状態共有と型付きハンドオフ契約で、コンテキスト溢れや無限委任を防ぐ。
5. **知識グラフをメモリとして使うパターン**: エージェントがエンティティ抽出→重複解決→関係構築→グラフ保存、というチェーンを組み、永続的な関係メモリとして活用する。

## 実装の成熟度レベル

1. **ホワイトボード段階**: 手動でレーンを分けてチャットやドキュメントで運用。自分が状態を管理する。
2. **ファイルトレイル**: 各ステップが`plan.md`・`research.md`・`review.md`などを書き出す。紙の軌跡を残す。
3. **オーケストレーション**: LangGraph、AutoGen GraphFlow、n8n等で状態チェックポイント・永続化・人間承認・並列/分岐/ループをコードで定義する。

各ノード内部では依然としてプロンプト・コンテキスト・エージェント・ループのエンジニアリングが動いており、グラフはそれらを「外側から調整する組織構造」に過ぎない。多くの本番システムでは、AIノードだけでなく決定論的な関数や人間チェックポイントを混ぜるのが成功の鍵。

## 実践5ステップ（Claude Code Dynamic Workflows）

Claude Code v2.1.154+の「Dynamic Workflows」機能を使い、1つのプロンプトから最大1,000エージェント（同時稼働は最大16）のグラフを組む実践ガイド。Max/Team/Enterpriseはデフォルト有効、Proは`/config`で有効化が必要。

1. **存在しないエッジを見つける**: 「AしてからBして、そしてCも」という指示に潜む偽の依存関係を疑う。「次のステップは本当に前の出力を読んでいるか？」と自問し、Noならエッジを引かず並列実行する。データが渡らない2つの箱は独立している。
2. **最初のグラフを作る**: リポジトリでプロンプトを投げると「Dynamic workflow requested」と表示され、Claudeが調整用のJSオーケストレーションスクリプトとフェーズ計画を作成する。承認すると1ファイル1エージェントなどの単位で艦隊が並列実行され（`/workflows`でライブ監視）、中間結果はスクリプト変数に残るため最終的に1つのレポートにまとまる。良い結果は`~/.claude/workflows`に保存し名前で再実行できる。ワークフローは通常セッションよりトークン消費が明らかに高い点に注意（節約されるのは「調整」部分のみ）。
3. **実際に壊れるところに備える**: (a) エージェントが自分の仕事を甘く採点する「自己同意」を防ぐため、実行者とは別の会話コンテキストを持つ独立したVerifierを置く。(b) 複数エージェントが同じgitコマンド等で衝突しないよう、危険なコマンドを禁止し各グループに独立したworktreeを与える。並列化前に「各エージェントはどこで作業するか」「結果はどうマージするか」「意見が割れたらどうするか」の3点を決めておく。
4. **本物のエッジを見つけてファンアウトし、独立コンテキストで検証し、作業者を隔離する**、という同じ形を様々な仕事（セキュリティ監査、引用付き調査レポート、モジュール移植、敵対的差分レビュー、定期的なエコシステム監視、未知件数の探索）に適用する。実例として、BunチームがZig→Rust移植（約53.5万行→100万行超）を約50ワークフロー・ピーク64エージェント並列・11日間・使用料約16.5万ドルで実行した事例がある（人間による設計と監視は必須、AIが書いた大量コードのレビュー体制が課題として指摘された）。
5. **グラフを正直に保つアンカーを置く**: トポロジーだけでは真実は保証されない。実際に走ったテスト・証拠に基づくVerifier・エージェントが調整できない凍結ルールの3つを「議論できない足場」として固定する。

**グラフが不要な場合**: タスクが小さく孤立している／全ステップを人間が読んで承認したい／何を探すべきかまだ分からない探索段階／ステップが本当に直列依存している（並列の余地がない）——このいずれかに該当するなら、グラフではなくループで十分。判断の目安は「2つの箱の間に矢印が1本も見つからなければグラフは存在しない」。

## 代表的なトポロジー（形状）パターン

| パターン | 構造のイメージ | 特徴・用途 |
| --- | --- | --- |
| Sequential（順次） | A → B → C | シンプルなパイプライン |
| Parallel（並列） | A → (B, C, D) → E | 独立タスクを同時実行し、後で集約 |
| Hierarchical（階層） | Supervisor → Worker群 | オーケストレーターが専門エージェントに仕事を振る |
| DAG（有向非巡回グラフ） | 依存関係に基づく実行 | 複雑な依存関係があるワークフロー |
| Network / Mesh | 全エージェントが相互に通信可能 | 明確な階層がない協調タスク |
| Loop / Cyclic | ノード間で循環 | 自己反省・再試行・改善ループ |
| Supervisor + Workers | 中央管理者が分岐・集約 | 最も実務で使われやすい |

これらを組み合わせて「fan-out（分散）→ 処理 → reduce（集約）→ verify（検証）」といった形を作るのが典型的。

## LangGraphでの実装（State / Node / Edge）

現在最も普及している実装の一つ（LangChain製）。3要素でグラフを定義する。

- **State（状態）**: グラフ全体で共有されるデータ構造（メッセージ履歴・中間結果・評価スコア・ツール呼び出し履歴等）。各ノードが読み書きでき、Reducer（集約関数）で並列更新をマージできる。
- **Nodes（ノード）**: 実際の処理を行う関数（LLM呼び出し、ツール実行、データ変換・評価・検証、人間の承認待ち）。「状態を受け取り→処理→更新された状態を返す」形。
- **Edges（エッジ）**: 次に進むノードを決める。固定エッジ（常にA→B）、条件付きエッジ（状態を見て「成功ならC、失敗ならD」と動的分岐）、並列エッジ（1ノードから複数ノードへ同時分岐＝fan-out）。実行は「スーパーステップ」単位で進み、メッセージパッシング方式で状態が伝播する。

```
pip install -U langgraph langchain-openai langchain-core
```

### 最小の例（State + Node + Edge）

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    text: str
    count: int

def node_a(state: State) -> dict:
    return {"text": state["text"] + " → A", "count": state["count"] + 1}

def node_b(state: State) -> dict:
    return {"text": state["text"] + " → B", "count": state["count"] + 1}

builder = StateGraph(State)
builder.add_node("a", node_a)
builder.add_node("b", node_b)
builder.add_edge(START, "a")
builder.add_edge("a", "b")
builder.add_edge("b", END)
graph = builder.compile()

result = graph.invoke({"text": "開始", "count": 0})
# => {'text': '開始 → A → B', 'count': 2}
```

### 条件分岐・ループ付きグラフ

`add_conditional_edges`にルーティング関数を渡すと、状態を見て次のノードを動的に決められる（例: `step`が3未満なら`step2`へ戻し、以上なら`END`へ進む）。エッジを逆向きにも張ることでループを構成できる。

### ReActエージェント（ツール呼び出し）

`MessagesState`とツールを組み合わせた基本形。LLMノードがツール呼び出しの要否を判断→`ToolNode`が実行→条件分岐（`should_continue`）でツール呼び出しがあれば`tools`ノードへ、なければ`END`へ。ツール実行後は再びLLMノードに戻るループ構成になる。

より簡潔に書きたい場合は`langgraph.prebuilt.create_react_agent`にモデルとツールのリストを渡すだけでReActエージェントを構築できる。

## 知識グラフとの違い

「グラフ」という言葉は2つの意味で使われるため注意が必要。

- **ワークフローグラフ**（本ページの主対象）: エージェントの実行フローを制御するもの。LangGraph等で実装。
- **知識グラフ（Knowledge Graph）**: エンティティと関係性を格納するデータ構造（例: Neo4j）。エージェントチームがデータを抽出して知識グラフを構築する使い方もあり、RAGの精度向上等に使われる。ワークフローグラフの中で知識グラフを操作するノードを置く組み合わせも一般的。

## 利点と注意点

**利点**: 制御フローの可視化・監査が可能、並列化による速度向上、失敗時の再試行・人間介入を明示的に埋め込める、役割分担が明確になり単一エージェントのコンテキスト限界を超えやすい、永続化（チェックポイント）により長時間実行・障害復旧が容易。

**注意点**: 設計が複雑になりがち（過剰設計を避ける）、状態の肥大化に注意（必要な情報だけ共有）、並列時の競合解決（tiebreak）をどう設計するかが重要、デバッグにはログと可視化ツールが必須。

## Context Engineeringを加えた3層スタック

数百エージェント規模のスワーム運用（Kimi K3を例にした事例）では、Loop・Graph に加えて **Context Engineering** を3層目として組み合わせる考え方が提示されている。

| レイヤー | 供給するもの | 欠けると起きること |
| --- | --- | --- |
| Loop | トリガー・ゲート・停止条件・予算上限 | 終わらない、または始まらない実行 |
| Graph | 根拠（evidence）付きの型付きノード・エッジ | 誰も問い合わせられない「毛玉」状態のグラフ |
| Context | 実行中の固定フォーマットな返却値＋実行後に残す2ファイル | 毎週ゼロからワークフローを再学習する羽目になる |

- **Loop側の暴走防止ガード**: ターン数上限、1回あたりのトークン予算上限、エージェント数の上限（300は天井であって既定値ではない。40ノードのタスクなら40エージェントで十分）、そして「前段の推論を一切見ていない状態でやり直すFresh-context Verifier」。自分が書いた答えを自分で採点する検証は甘くなりやすいため、最後のガードが特に重要。
- **Graphのスキーマ設計原則**: ノードは「後で質問する対象になるもの」（例:「Stripe」はノード、「Stripeが2021年に資金調達した」はそのノードに属する事実）。すべてのエッジに型と出典を持たせる。正規化した名称でマージしてから接続する（表記ゆれのまま繋ぐとクラスタが分裂する）。関連度の閾値を設け、何でも繋がない。
- **Contextの2つの問題は別物**: (1) 実行中のウィンドウ問題＝多数のエージェントの返り値をオーケストレーターが集約しきれなくなる。対策は各エージェントに自由文ではなく固定スキーマ（`node_id`・`sources`・`candidate_edges`・`confidence`等）で返させること。(2) セッションを超えて何が残るかという問題＝ウィンドウの外、`SKILL.md`（うまくいった手順・入力形式・返却スキーマ）と`CONSTRAINTS.md`（過去の実行で見つかった訂正事項・見落とし）の2ファイルに記録する。制約ファイルのないスキルファイルは速くなるだけだが、制約ファイルがあるスキルファイルは速くなった上で同じ失敗を繰り返さなくなる——これが「記憶」として機能する条件。
- 100万トークンのコンテキストウィンドウは「記憶」ではなく、あくまで1回のセッション内で推論するための一時的な作業領域に過ぎない、という指摘は[[エージェントメモリ設計]]のWorking Memory/Long Term Memoryの区別と対応する。
